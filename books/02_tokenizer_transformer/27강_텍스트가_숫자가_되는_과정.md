# 27강. 텍스트가 숫자가 되는 과정
## 이번 강에서 배우는 내용

- 컴퓨터가 왜 텍스트를 곧바로 행렬곱에 넣지 못하는지
- Encoding Pipeline(인코딩 파이프라인)이 텍스트에서 token id까지 어떻게 흐르는지
- Character Code(문자 코드)와 Token(토큰)의 차이
- GPT 계열 모델이 추론·학습할 때 실제로 보는 입력이 무엇인지

## 왜 중요한가?
LLM을 “대화하는 AI”로만 보면, 내부는 마법처럼 보인다. 실제로 일어나는 일은 훨씬 단순하고 기계적이다.

```text
사용자: "오늘 날씨 어때?"
  → Tokenizer가 문자열을 조각내고 정수로 바꾼다
    → Embedding이 정수를 벡터로 바꾼다
      → Transformer가 벡터 서열을 처리한다
        → Softmax가 다음 토큰 확률을 만든다
          → 다시 문자열로 디코딩한다
```

이 파이프라인에서 **첫 변환이 잘못되면** 뒤의 모든 층이 쓸모없어진다.  
“좋은 Attention”을 배우기 전에, 모델이 **무엇을 보고 있는지**를 고정해야 한다.

## 선수 개념
1권에서 이미 익힌 것들을 짧게 복기한다.

| 개념 | 위치 | 이번 강의에서의 역할 |
|---|---|---|
| Tensor | 9·19강 | token id, embedding, logit이 모두 Tensor |
| Matrix Multiplication | 10강 | Embedding lookup 이후의 Linear/Attention |
| Softmax 직관 | 13강 | 다음 토큰 점수를 확률로 |
| Dataset / 배치 | 22강 | id 서열을 배치로 모은다 |
| Next Token Prediction | 1·26강 | 목표: 다음 id를 맞힌다 |

아직 몰라도 되는 것:

- BPE merge 규칙의 상세 (29강)
- Attention 수식 (이후 강의)
- Cross Entropy의 엄밀한 정의 (34강)

## 핵심 개념
### 3.1 텍스트는 사람이 읽고, 숫자는 모델이 계산한다

**Text(텍스트)**는 사람이 읽는 문자 열이다. 예: `"cat"`, `"안녕하세요"`.

**Neural Network(신경망)**의 기본 연산은 덧셈·곱셈·비선형 함수이다. 문자열 `"cat"`에 직접 행렬을 곱할 수 없다.

따라서 반드시 중간 표현이 필요하다.

```text
사람용 표현:  "The cat sat"
모델용 표현:  [464, 3797, 3332]   ← 예시 token id
```

이 정수들이 **Token ID(토큰 아이디)**이다.

### 3.2 Token (토큰)

**Token(토큰)**은 텍스트를 나눈 **모델 처리의 최소 단위**이다.

왜 “단어”라고 바로 말하지 않는가?

- 어떤 시스템은 글자 단위를 쓴다.
- 어떤 시스템은 단어 단위를 쓴다.
- 현대 LLM은 대개 **Subword(부분 단어)** 단위를 쓴다.

토큰의 예 (개념적):

```text
문장: "unhappiness"
가능 분할 1 (단어):   ["unhappiness"]
가능 분할 2 (글자):   ["u","n","h","a","p","p","i","n","e","s","s"]
가능 분할 3 (서브워드): ["un", "happiness"] 또는 ["un", "happi", "ness"]
```

같은 문장도 Tokenizer 설계에 따라 조각 수와 id가 달라진다.

### 3.3 Vocabulary (어휘 사전)

**Vocabulary(보캐뷸러리, 어휘 사전)**는 모델이 알 수 있는 토큰들의 집합과, 각 토큰에 붙인 정수 id의 대응표이다.

```text
"the" → 464
"cat" → 3797
"sat" → 3332
...
```

- Vocabulary 크기 $V$가 크면: 표현은 세밀해지지만 Embedding 행렬이 커진다.
- Vocabulary 크기가 작으면: 압축·일반화는 쉬워질 수 있지만, 같은 문장이 더 많은 토큰으로 쪼개질 수 있다.

상세는 30강에서 다룬다.

### 3.4 Encoding Pipeline (인코딩 파이프라인)

**Encoding Pipeline(인코딩 파이프라인)**은 원문 텍스트를 모델 입력용 숫자 서열로 바꾸는 일련의 단계이다.

전형적인 흐름:

```text
1) 원문 텍스트 (Unicode 문자열)
2) (선택) 정규화: 공백, 대소문자, NFKC 등
3) Tokenization: 문자열 → 토큰 목록
4) Token → ID: 토큰 목록 → 정수 목록
5) (선택) Special Token 삽입: BOS/EOS/PAD 등
6) (학습 시) 패딩·배치·attention mask 구성
```

디코딩은 대략 역방향이다.

```text
token ids → 토큰 문자열들 → 이어 붙여 텍스트
```

주의: 인코딩과 디코딩이 **완전 대칭**이 아닐 수 있다. (정규화, 공백 규칙, special token 처리 때문에)

### 3.5 Character Code vs Token ID

초보자가 가장 자주 섞는 구분이다.

**Character Code(문자 코드)**는 Unicode/UTF-8 같은 **문자 인코딩**의 숫자이다.

```python
ord("A")   # 65
ord("안")  # 50504
```

**Token ID**는 Tokenizer의 Vocabulary에 속한 **학습/모델용 인덱스**이다.

| 구분 | Character Code | Token ID |
|---|---|---|
| 무엇을 가리키나 | 글자 하나의 표준 코드 | 토큰 하나의 모델 id |
| 누가 정의하나 | Unicode 표준 | Tokenizer / 모델 제작자 |
| 범위 예시 | `0`~`0x10FFFF` (이론상) | `0` ~ `V-1` |
| 모델 입력으로 쓰나 | 거의 안 씀 (특수 실험 제외) | 항상 씀 |

예:

```text
문자 "A"의 코드포인트: 65
어떤 GPT Tokenizer에서 "A" 토큰 id:  (모델마다 다름, 예: 32가 아님)
```

즉, `ord()`로 얻은 숫자를 Embedding에 넣으면 **그 모델의 Vocabulary와 무관한 잘못된 입력**이 된다.

### 3.6 왜 “바이트”만으로 충분하지 않은가

이론상 UTF-8 바이트(0~255)만으로도 모든 텍스트를 표현할 수 있다. 실제로 Byte-level BPE도 바이트에서 출발한다.

하지만 바이트 하나 = 의미 단위는 아니다.

```text
"고양이"
UTF-8 바이트는 여러 개
의미 단위는 "고양이" 또는 "고", "양이" 같은 조각일 수 있음
```

좋은 Tokenizer는 **짧은 서열로도 의미를 담을 수 있게** 자주 나오는 조각을 묶는다. 이것이 Subword / BPE의 동기이다 (28·29강).

## 직관적으로 이해하기
도서관 비유를 쓴다.

1. 책에 적힌 문장 = 텍스트
2. 사서의 “청구 기호 체계” = Vocabulary
3. 각 단어/구에 붙인 번호표 = Token ID
4. 번호표를 보고 서가에서 책을 꺼내는 일 = Embedding lookup (31강)

모델은 문장의 “모양”을 보는 게 아니라, **번호표 서열**을 본다.

```text
"I love cats"
→ [40, 1862, 19909]   # 가상의 id
```

같은 의미의 다른 표현:

```text
"I love cat s"  (공백·분할이 달라지면)
→ 다른 id 서열이 될 수 있다
```

따라서 “모델이 문장을 이해한다”는 말은, 정확히는 **토큰 id 서열의 통계적 패턴을 학습한다**에 가깝다.

## 작은 숫자로 직접 보기
아주 작은 Vocabulary를 가정한다.

```text
Vocabulary:
  "I"    → 0
  "love" → 1
  "cats" → 2
  "dogs" → 3
  "."    → 4
```

문장:

```text
"I love cats."
```

토큰화(단어 단위라고 가정):

```text
["I", "love", "cats", "."]
```

id 서열:

```text
[0, 1, 2, 4]
```

다음 토큰 예측 관점:

```text
문맥 [0, 1, 2] 를 보고
다음이 4(".") 일 확률을 높이고 싶다
```

학습 데이터에서는 보통 이렇게 쌍을 만든다.

```text
입력:  [0, 1, 2]
정답:  [1, 2, 4]   # 한 칸씩 밀어 쓴 next-token 타깃 (상세 32강)
```

이 작은 예만으로도 “텍스트 → id → 예측 목표”의 골격이 보인다.

## 코드로 구현하기
아래는 **교육용 초소형 Tokenizer**이다. 실전 BPE가 아니라, 파이프라인 감각을 고정하기 위한 코드다.

```python
# tiny_pipeline.py
# 목적: 텍스트 → 토큰 → id → (가짜) 디코딩 흐름을 손으로 확인

from typing import Dict, List

class TinyWordTokenizer:
    """공백 기준 단어 Tokenizer + 고정 Vocabulary."""

    def __init__(self, vocab: Dict[str, int]):
        self.token_to_id = dict(vocab)
        self.id_to_token = {i: t for t, i in vocab.items()}
        # UNK: Unknown Token (모르는 토큰)
        if "<unk>" not in self.token_to_id:
            raise ValueError("Vocabulary에 <unk>가 필요합니다.")

    def tokenize(self, text: str) -> List[str]:
        # 아주 단순한 규칙: 소문자화 + 공백 split
        # 실전 Tokenizer는 Punctuation, Unicode 정규화 등을 꼼꼼히 처리한다.
        return text.lower().split()

    def encode(self, text: str) -> List[int]:
        tokens = self.tokenize(text)
        unk = self.token_to_id["<unk>"]
        return [self.token_to_id.get(t, unk) for t in tokens]

    def decode(self, ids: List[int]) -> str:
        tokens = [self.id_to_token.get(i, "<unk>") for i in ids]
        return " ".join(tokens)

def demo() -> None:
    vocab = {
        "<unk>": 0,
        "i": 1,
        "love": 2,
        "cats": 3,
        "dogs": 4,
        ".": 5,
    }
    tok = TinyWordTokenizer(vocab)

    text = "I love cats ."
    ids = tok.encode(text)
    recovered = tok.decode(ids)

    print("text     :", text)
    print("token ids:", ids)
    print("decoded  :", recovered)

    # 모르는 단어는 <unk> id로 간다
    print("OOV ids  :", tok.encode("I love birds ."))

if __name__ == "__main__":
    demo()
```

실행 결과 예시:

```text
text     : I love cats .
token ids: [1, 2, 3, 5]
decoded  : i love cats .
OOV ids  : [1, 2, 0, 5]
```

여기서 확인할 점:

1. 모델이 받는 것은 문자열 `"cats"`가 아니라 정수 `3`이다.
2. Vocabulary에 없는 `"birds"`는 `0`(`<unk>`)이 된다. → **OOV(Out-of-Vocabulary)** 문제 (28강).
3. 디코딩은 근사적으로 원문을 복원한다. 대소문자·정확한 문장부호는 이 단순 규칙으로는 보존되지 않는다.

## PyTorch로 “모델 입력” 형태로 만들기
학습/추론에서는 id 목록을 Tensor로 올린다.

```python
import torch

# 배치 크기 2, 서열 길이 4
batch_ids = torch.tensor(
    [
        [1, 2, 3, 5],  # I love cats .
        [1, 2, 4, 5],  # I love dogs .
    ],
    dtype=torch.long,
)

print(batch_ids.shape)  # torch.Size([2, 4])
print(batch_ids.dtype)  # torch.int64
```

중요한 관례:

- Token id는 보통 `torch.long` / `int64`이다.
- Embedding 층은 이 정수를 **인덱스로** 사용한다 (31강).
- 아직 이 Tensor는 “의미 벡터”가 아니다. **단지 사전 번호표**이다.

## LLM에서는 어디에 사용될까?
공개 GPT 계열·오픈소스 LLM의 공통 패턴:

```text
prompt 텍스트
  → 해당 모델 전용 Tokenizer.encode(...)
    → input_ids: shape [batch, seq_len]
      → model(input_ids)
        → logits: shape [batch, seq_len, vocab_size]
          → (생성 시) 마지막 위치 분포에서 다음 id 샘플/탐욕 선택
            → Tokenizer.decode(...)
```

실무에서 자주 보는 이름:

| 이름 | 의미 |
|---|---|
| `input_ids` | 모델에 들어가는 token id Tensor |
| `attention_mask` | 패딩 위치를 가리키는 마스크 |
| `labels` / `labels_ids` | 학습 시 next-token 정답 id |
| `tokenizer` | Hugging Face 등에서 인·디코더 객체 |

모델 체크포인트와 Tokenizer는 **한 세트**이다.  
A 모델의 id를 B 모델 Embedding에 넣으면 의미가 완전히 깨진다.

챗 모델에서는 추가로 대화 템플릿이 붙는다.

```text
system / user / assistant 역할 문자열
  + special tokens (<|im_start|>, <|eot_id|> 등)
    → 하나의 token id 서열
```

Special Token의 역할은 30강에서 다룬다.

## 자주 하는 실수
1. **`ord()` / UTF-8 바이트를 token id로 착각**  
   모델 Vocabulary와 무관한 숫자이다.

2. **Tokenizer 없이 Embedding만 만진다**  
   “고양이” 문자열을 직접 `nn.Embedding`에 넣을 수 없다. 먼저 id가 필요하다.

3. **다른 모델의 Tokenizer로 encode한 id를 사용**  
   id 공간이 다르면 Embedding 행이 다른 토큰을 가리킨다.

4. **디코딩이 항상 원문 복원이라고 믿음**  
   정규화·special token·공백 규칙 때문에 완전 복원이 아닐 수 있다.

5. **토큰 = 단어라고 단정**  
   현대 LLM은 대개 Subword이다. 28강에서 비교한다.

## 핵심 요약
- 신경망은 문자열을 직접 계산하지 못한다. **Token ID**가 다리이다.
- **Encoding Pipeline**: 텍스트 → 토큰 → id (→ special token/배치).
- **Character Code**와 **Token ID**는 다른 세계이다 숫자이다.
- LLM이 실제로 학습·추론하는 입력의 첫 형태는 `input_ids` Tensor이다.
- 이후 강의는 이 id를 **어떻게 자르는지(28·29)**, **사전과 특수 토큰(30)**, **벡터로 바꾸는지(31)**, **다음 id를 어떻게 예측하는지(32·33)**로 이어진다.

## 용어 사전
| 용어 | 의미 |
|---|---|
| Token (토큰) | 텍스트를 나눈 모델 처리 단위 |
| Token ID | Vocabulary 상의 정수 인덱스 |
| Vocabulary (어휘 사전) | 토큰 ↔ id 대응 집합 |
| Encoding Pipeline | 텍스트를 id 서열로 바꾸는 단계들 |
| Decoding | id 서열을 다시 텍스트로 복원하는 과정 |
| Character Code | Unicode 등 문자 표준의 코드 값 |
| OOV | Vocabulary에 없는 토큰/단어 |
| `input_ids` | 모델에 들어가는 token id Tensor |

신경망의 기본 연산이 수치 연산이기 때문이다. 텍스트를 이산적인 id로 바꾼 뒤 Embedding으로 벡터화해야 Linear/Attention을 적용할 수 있다.

### 문제 2

보장되지 않는다. `ord`는 Unicode 표준 코드이고, token id는 특정 Tokenizer Vocabulary의 인덱스이다. 체계가 다르다.

### 문제 3 예시

원문 → (정규화) → Tokenization → Token→ID 매핑 → (Special Token) → (패딩/배치)

### 문제 4

### 문제 5
