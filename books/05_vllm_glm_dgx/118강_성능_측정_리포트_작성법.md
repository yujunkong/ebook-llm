# 118강. 성능 측정 리포트 작성법
## 이번 강에서 배우는 내용

- 프로젝트 지침의 필수 보고 필드 11개로 모든 결과 행을 검증한다
- 허위·전언·출처 없는 가속 수치를 걸러내는 검수 목록을 적용한다
- 빈 칸 템플릿과 “예시 레이블” 표만으로 보고서 골격을 완성한다
- 제119강 운영 체크리스트에 넘길 알려진 한계·재현 절차를 적는다

## 왜 중요한가?
같은 GPU에서도 다음이 바뀌면 수치가 바뀐다.

- 엔진 버전·커널 플래그
- 입력/출력 길이·동시성
- 클럭·전력·온도·백그라운드 잡
- 측정 코드의 시계 위치（클라이언트 vs 서버）

그래서 “빠르다”는 문장은 리포트가 아니다. 리포트는 **조건 집합 → 측정 절차 → 결과 → 한계**의 묶음이다. 제66·75강의 eval 리포트 습관이 Serving 지표로 확장된 형태다.

## 프로젝트 지침과의 관계
`docs/PROJECT_GUIDELINES.md` 핵심:

> 성능 수치는 임의로 만들지 않는다.

본 강의가 강제하는 **벤치마크 보고 템플릿** 최소 스키마:

| # | 필드 | 영문 키 | 설명 |
|---:|---|---|---|
| 1 | 모델 | `model` | 체크포인트 이름·리비전·경로 |
| 2 | 양자화 | `quant` | bf16/fp8/int4-awq 등 |
| 3 | GPU | `GPU` | 장치 제품명 |
| 4 | 대수 | `count` | 사용 GPU 수 |
| 5 | 컨텍스트 | `context` | 입력·최대출력 토큰 설계 |
| 6 | 배치 | `batch` | 동시성/`max_num_seqs` 등 |

한 칸이라도 비거나 “대략 A100”처럼 모호하면 그 행은 **초안**이지 보고 행이 아니다.

| 독자 | 리포트에서 찾는 것 |
|---|---|
| 미래이 자신 | 재실행 명령·설정 해시 |

## 필드별 작성 규칙
### 7.1 model

- Hugging Face ID만이 아니라 **리비전·로컬 경로 해시**를 가능하면 적는다.
- chat/instruct 변형을 base와 섞지 않는다.
- 토크나이저·chat template 불일치 가능성을 `methods.md`에 한 줄 적는다.

### 7.2 quant

권장 표기:

```text
bf16 | fp16 | fp8 | int8-w8a8 | int8-weight-only | int4-awq | int4-gptq | ...
```

“4bit”만 쓰고 포맷·캘리브 데이터·커널을 숨기지 않는다.

### 7.3 GPU · count

- `nvidia-smi -L`의 이름
- 동일 제품이라도 MIG·클럭 잠금 여부를 `env_snapshot`에
- `count`는 **실제 사용 수**. 머신에 8장이 있어도 2장만 쓰면 2

### 7.4 context

권장 문자열:

```text
in_tokens=1024, max_out_tokens=128, template=chat_vX
```

프롬프트 파일 해시:

```bash
sha256sum prompts/medium.txt
```

### 7.5 batch

모호한 “batch=32” 금지. 다음 중 명시:

- 클라이언트 concurrency `c=32`
- 엔진 `max_num_seqs=32`
- offline true batch（엔진이 지원하고 정의가 문서와 일치할 때）

### 7.6 framework · version

```text
framework=vLLM
version=vllm==X.Y.Z; torch==…; cuda=…; driver=…
```

TRT-LLM·SGLang도 같은 규칙. “최신”이라는 단어는 버전이 아니다.

### 7.7 method

최소 포함:

1. 부하 유형（sync_serial / async_conc_K / engine_bench）
2. warm-up 횟수, measure 횟수
3. 시계 위치（client first-byte / server log）
4. 평균인지 p50/p95인지
5. 네트워크 구간 포함 여부（localhost vs remote）

### 7.8 metric

이름을 표준화한다.

| 권장 키 | 의미 |
|---|---|
| `TTFT_p50_s` | 첫 토큰 지연 중앙값（초） |
| `TTFT_p95_s` | 95 백분위 |
| `TPOT_mean_s` | 토큰당 시간 평균 |
| `throughput_req_s` | 요청/초 |
| `throughput_tok_s` | 출력 토큰/초 |
| `vram_peak_MiB` | 피크 메모리 |

단위를 키에 붙이거나 `metric`+`unit` 열을 둔다. `TTFT`만 적고 단위를 숨기지 않는다.

### 7.9 result

허용:

- 실측 숫자 + 단위
- `FAIL` / `N/A` + note
- 빈 칸（아직 미측정）

금지:

- 마케팅 블로그 수치
- “대략 2배”
- 다른 모델·다른 GPU에서 가져온 숫자
- 조건 열을 비운 채 결과만 채움

## JSONL 스키마（기계 판독）
```json
{
  "model": "",
  "quant": "",
  "GPU": "",
  "count": 0,
  "context": "",
  "batch": "",
  "framework": "",
  "version": "",
  "method": "",
  "metric": "",
  "result": null,
  "unit": "",
  "ok": true,
  "note": "",
  "run_id": "",
  "timestamp": ""
}
```

검증 스크립트 스케치:

```python
REQUIRED = [
    "model", "quant", "GPU", "count", "context", "batch",
    "framework", "version", "method", "metric", "result",
]

def validate_row(d: dict) -> list[str]:
    errors = []
    for k in REQUIRED:
        if k not in d or d[k] in ("", None):
            # result만 예외적으로 null 허용(미측정). 보고 확정 단계에선 숫자/FAIL 필요.
            if k == "result":
                continue
            errors.append(f"missing:{k}")
    return errors
```

**보고 확정본**에서는 `result`가 `null`이면 CI/검수에서 실패로 두는 것을 권장한다.

## methods.md — 절차를 글로 고정
체크리스트:

- [ ] 프롬프트 집합과 해시
- [ ] 샘플링 파라미터（temperature 등）
- [ ] 워밍업·본측정 횟수
- [ ] 이상치 제거 규칙（있으면）. “맘에 안 들어 삭제” 금지
- [ ] 동시 실행 금지 조건（다른 GPU 잡）
- [ ] 시간대·전원 모드（가능하면）

작은 숫자 예（**횟수만 예시**, 성능 아님）:

```text
warm-up runs: 3
measured runs: 10
aggregate: p50 for latency, mean for tok/s
```

## analysis.md — 사실과 가설 분리
강제 문체:

```text
[사실] rows.md의 run_id=A와 run_id=B를 비교하면 metric=M에서 A < B 이다.
[가설] 원인은 KV 메모리 대역 압박일 수 있다.
[검증 필요] nsys/엔진 메트릭으로 prefill 시간을 분해한다.
[결정] 다음 실험은 Context 축을 고정하고 Batch만 재측정한다.
```

사실 문장에 가설 동사를 넣지 않는다（“개선되었을 것이다” 금지）.

## 시각화 규칙
그래프를 쓸 때:

1. 축에 단위
2. 범례에 quant/batch/context 중 **비교 축**만 색으로
3. 제목에 framework version
4. 오차 막대 또는 표본 수 N

막대 그래프에 서로 다른 method를 붙여 “우승”을 만들지 않는다.

## 실습
1. 117의 임의 3행을 골라 11필드 표로 옮긴다（result는 실측 또는 공란）.
2. 의도적으로 잘못된 행 2개를 만들고（버전 누락, method 혼입）검수 목록으로 잡는다.
3. `analysis.md`에 사실/가설/검증필요/결정 각 1문장.
4. 타인（또는 이틀 후 자신）이 `replay.md`만 보고 재실행 가능한지 읽기 테스트를 한다.

## 자주 하는 실수
1. 엑셀에는 숫자, 문서에는 조건 — 둘이 분리되면 조건이 유실된다.
2. “평균”만 보고 꼬리 지연（p95）을 숨긴다.
3. 토큰/초와 요청/초를 같은 열에 섞는다.
4. 프레임워크만 바꾸고 모델 양자화·최대 길이까지 몰래 바꾼다.
5. 리포트를 챗 응답 갤러리로 대체한다.

## 정답 및 해설
### 문제 1

model, quant, GPU, count, context, batch, framework, version, method, metric, result.

### 문제 2

예: 임의로 만든 수치, 출처 없는 배수, 타 환경 수치를 우리 결과처럼 재라벨.

### 문제 3

재현·비교 불능. 초/밀리초, p50/평균, 클라이언트/서버 중 무엇을 잰지 몰라 의사결정이 오염된다.

### 문제 4

질문: “이 행만 보고 다른 사람이 같은 실험을 다시 켤 수 있는가?” / 예: 숫자만 있는 슬라이드, 챗봇 스크린샷 모음.

### 문제 5

예 — [사실] 동일 method 행에서 metric=vram_peak_MiB의 result가 quant=bf16 행보다 quant=int4 행에서 작다. [가설] 가중치 비트 감소가 주원인일 수 있다.

### 문제 6

`artifacts/runs/*.jsonl`의 측정 행（또는 동등한 원시 로그）.
