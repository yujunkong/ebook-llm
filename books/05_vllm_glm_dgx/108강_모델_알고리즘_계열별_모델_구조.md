# 5권. vLLM · GLM · DGX Spark

## 제108강. 모델 알고리즘 계열별 모델 구조

### 1. 이번 강의에서 배울 것

제104~107강은 **엔진·스케줄·지표** 쪽이었다. 같은 vLLM이라도 올리는 가중치의 **알고리즘 계열**이 바뀌면 KV, 계산, 통신, 심지어 “토큰을 몇 개씩 예측하는지”가 달라진다. 이번 강의는 특정 제품 하나만의 해부가 아니라, **계열 지도**를 그린다.

이 강의를 마치면 다음을 말할 수 있어야 한다.

- Dense causal Transformer(decoder-only)의 공통 골격
- MoE가 Dense와 갈라지는 지점(전문가·라우터) — 상세는 제109강
- Multi-token prediction / 스펙큘레이티브와 맞닿는 구조 변이 — 제110강 예고
- Hybrid / SSM 계열이 Attention-only와 달리 서빙에 던지는 질문
- GLM · LLaMA · Qwen 등을 **계열 안의 사례**로 어디에 올려 놓는지

**사실:** 상용·오픈 모델 이름은 마케팅·라이선스·체크포인트 단위로 자주 바뀐다.  
**해석:** “LLaMA 계열 = 영원히 이 하이퍼파라미터”가 아니다. 아래는 **구조 패턴** 분류다. 구체 층 수·헤드 수·전문가 수는 해당 모델 카드·논문을 본다.

### 2. 왜 이것을 배우는가

서빙 엔지니어가 모델 카드를 읽을 때 필요한 질문은 브랜드가 아니라 다음이다.

```text
1) 매 decode 스텝에 무엇이 커지는가? (KV? 상태?)
2) 파라미터 중 몇 %가 매 토큰에 활성화되는가?
3) 한 스텝에 토큰을 몇 개 후보로 내는가?
4) 커널·엔진이 그 패턴을 지원하는가?
```

계열을 모르면 TTFT/TPOT 이상치를 “엔진 버그”로만 의심하게 된다.

### 3. 먼저 알아야 할 개념

1. Causal LM · Self-Attention · FFN (2권, 3권)
2. KV Cache (제101강)
3. 서빙 지표 TTFT/TPOT/Throughput (제107강)
4. (연결) MoE 상세 → 제109강, MTP/Speculative → 제110강

### 4. 계열 지도 — 한눈에

```text
                    ┌─ Dense Decoder-only Transformer
Autoregressive LM ─┼─ MoE Decoder-only (sparse FFN)
                    ├─ MTP / multi-token heads (훈련·추론 변이)
                    └─ Hybrid: Attention + SSM/Linear-RNN 등
```

직교 축(섞일 수 있음):

| 축 | 예 |
|---|---|
| 밀도 | Dense vs MoE |
| 시퀀스 믹싱 | Softmax Attention vs SSM/linear |
| 예측 폭 | Next-token vs multi-token |
| 위치 | RoPE 등 (세부는 모델별) |

### 5. Dense causal Transformer（기본 골격）

#### 5.1 블록

전형적인 decoder-only 블록:

$$
\begin{aligned}
x &\leftarrow x + \mathrm{Attn}(\mathrm{Norm}(x)) \\
x &\leftarrow x + \mathrm{FFN}(\mathrm{Norm}(x))
\end{aligned}
$$

- **Attn:** causal self-attention → 서빙 시 **KV cache** 성장
- **FFN/MLP:** 토큰별 밀집 변환 → decode에서 종종 **메모리 대역폭** 민감

#### 5.2 서빙 함의

| 항목 | Dense decoder-only |
|---|---|
| KV | 층×헤드×길이×dtype — 동시성 한계의 주범 중 하나 |
| 활성화 파라미터 | 매 토큰 거의 전체 MLP+Attn |
| 엔진 지원 | vLLM 등에서 가장 넓게 검증된 패턴 |
| 지표 | 긴 입력 → TTFT, 긴 출력·다중 세션 → TPOT·KV |

#### 5.3 사례로 올리는 이름（브랜드 ≠ 계열 정의）

| 사례(예시) | 읽어 두는 포인트 |
|---|---|
| **LLaMA** 계열 | Pre-norm, RoPE, SwiGLU식 FFN 등 **Dense decoder-only** 템플릿의 대표적 오픈 계보 |
| **Qwen** Dense 체크포인트 | 같은 Dense 골격 위의 데이터·스케일·토크나이저·길이 확장 등 **제품 축** 차이 |
| **GLM** Dense/대화 체크포인트 | 역시 decoder-only Transformer 계열 안의 한 갈래; **GLM 단독 구조론으로 이 강을 축소하지 말 것** |

**사실:** 각 세대(LLaMA 2/3, Qwen2/3, GLM-4 등)마다 세부 블록이 갱신된다.  
**해석:** 서빙 관점의 1차 분류는 “이름”이 아니라 **Dense + KV-growing Attention + dense FFN** 여부다.

### 6. MoE Decoder-only（개요만 — 제109강으로）

FFN을 **전문가(expert)** 여러 개로 복제하고, **라우터**가 토큰마다 소수만 고른다.

$$
y=\sum_{e\in\mathrm{TopK}(x)} g_e(x)\,E_e(x)
$$

서빙 미리보기:

- **총 파라미터**는 커도 **활성 파라미터**는 작을 수 있음 → FLOPs/토큰 이야기와 메모리(전문가 가중치 상주) 이야기가 분리됨
- Expert parallel / 통신, 부하 불균형, 엔진의 MoE 커널 지원 여부가 TTFT/TPOT에 개입

상세·라우팅·서빙 함의는 **제109강. MoE**.

### 7. Multi-token prediction 변이（개요 — 제110강으로）

표준 LM은 한 스텝에 다음 토큰 하나. **MTP(Multi-Token Prediction)** 계열은 훈련·아키텍처에서 **여러 미래 토큰**을 함께 예측하도록 설계된 변이를 가리키는 경우가 많다. 추론에서는 **스펙큘레이티브 디코딩**의 draft로 이어지기도 한다.

서빙 미리보기:

- 수락률이 높으면 **유효 TPOT** 개선 여지
- draft/verify 두 경로·커널 융합·엔진 플래그 의존
- “모델이 MTP를 안다”와 “서버가 speculative을 켠다”는 **별개 스위치**일 수 있음

상세는 **제110강. MTP와 Speculative Decoding**.

### 8. Hybrid / SSM 개요

#### 8.1 동기

Softmax Attention의 KV는 길이 $T$에 비례해 늘어난다. **SSM(State Space Model)** · 선형 RNN 계열은 시퀀스를 **고정 크기 상태**로 압축·갱신하려는 동기를 공유하는 경우가 많다(모델마다 수식 상이).

#### 8.2 Hybrid

실무·연구 모두에서 흔한 패턴은 **일부 층 Attention + 일부 층 SSM/linear** 혼합이다. 장문·효율을 노리되, 필요한 곳에는 완전한 attention을 남긴다.

#### 8.3 서빙 함의（교육용）

| 질문 | Attention Dense | SSM/Hybrid |
|---|---|---|
| Decode 상태 | KV 캐시(길이 비례) | 고정 상태에 가깝게 설계된 경우 있음 |
| Prefill | 병렬 attention에 강점 | 구현·커널 성숙도가 엔진마다 다름 |
| 엔진 | 지원 넓음 | **지원 행렬·버전을 반드시 확인** |
| 지표 | KV OOM·paging이 중심 | 상태 dtype·커널 효율·하이브리드 비율이 중심 |

**사실:** “SSM이면 KV가 없어서 항상 더 빠르다”는 문장은 성립하지 않는다. 하이브리드에 attention 층이 남으면 KV가 남고, 커널이 미성숙하면 Dense Transformer보다 느릴 수 있다.  
**해석:** 계열 선택 = 품질·길이·생태계·서빙 스택의 **연립 방정식**이다.

### 9. 구조를 서빙 변수에 매핑

```text
구조 선택
  ├─ Attention 비중 ↑  → KV 메모리 ↑ → 동시성·PagedAttention 중요
  ├─ Dense FFN        → 대역폭·양자화 민감
  ├─ MoE              → 가중치 상주 메모리 + 라우팅/통신
  ├─ MTP/Speculative  → 스텝당 확정 토큰 ↑ 시도 (수락률 조건)
  └─ SSM/Hybrid       → 상태 크기·커널·엔진 지원 확인
```

제107강 템플릿의 `model` 필드에는 이름뿐 아니라 **계열 태그**를 적는 습관을 권한다. 예: `Dense-Decoder`, `MoE-Decoder`, `Hybrid-Attn-SSM`.

### 10. 작은 비교 표（수치 주장 없음）

| 계열 | 매 토큰 활성 계산 | 길이 상태 | 서빙에서 먼저 볼 것 |
|---|---|---|---|
| Dense decoder-only | Attn+FFN 전체 | KV ∝ T | KV, Continuous batch |
| MoE | Attn+소수 Expert | KV ∝ T (보통) | Expert 배치·RAM, 라우팅 |
| MTP/Speculative | draft+verify | KV + draft 버퍼 | 수락률, 추가 커널 |
| Hybrid/SSM | 층 구성 의존 | KV 일부 + 상태 | 엔진 지원, 혼합비 |

숫자는 모델 카드·자체 측정으로만 채운다.

### 11. 코드로 “계열 감지”가 아니라 “체크리스트”

모델 구현을 열 때 질문 리스트:

```python
checklist = {
    "decoder_only_causal": True,   # 마스크·KV 가정
    "ffn_is_moe": False,           # True면 expert 수·topk 기록
    "num_attention_layers": None,  # hybrid면 attn 층만
    "has_ssm_or_linear_layers": False,
    "multi_token_heads": False,    # MTP 관련
    "rope_or_other_pe": "unknown",
}
# 서빙 티켓에 checklist를 붙여 TTFT/TPOT 해석에 사용
```

자동 감지에 의존하지 말고 **문서·config.json·논문**을 교차 확인한다.

### 12. 계열별 “서빙 질문 카드”

실무에서 모델 카드를 읽을 때 한 장에 적는다.

```text
[Family Card]
name: <checkpoint>
family: Dense-Decoder | MoE-Decoder | Hybrid | Other
attention_layers: <n or unknown>
ffn: dense | moe(E=?,k=?)
state: kv_only | kv+ssm | other
prediction: next_token | mtp | speculative_ready
engine_support: <engine==version → yes/no/partial>
kv_growth: yes/no/partial
notes: <license, max len, quant recipes>
```

이 카드가 비어 있으면 제107강 리포트의 `model` 필드도 빈약한 것이다.

### 13. Dense 블록을 서빙 비용으로 분해

토큰 하나 decode(이상화):

1. Norm + QKV 투영 — 가중치 읽기
2. Attention with KV — KV 읽기/쓰기 + compute
3. O 투영
4. FFN — 종종 **가장 큰 가중치 읽기**
5. LM head (마지막 층 후)

**해석:** 많은 Dense 모델의 decode는 FLOPs 한계보다 **가중치·KV 대역폭**에 가깝다(제111강).  
**사실:** 정확한 바운드 비율은 모델 폭·양자화·커널·배치에 의존 — 측정 전 단정 금지.

장문 prefill에서는 Attention의 $T$ 의존 항이 도드라질 수 있다(제52·100강 감각).

### 14. GQA/MQA — Dense 안의 중요한 변형

Multi-Head에서 더 나아가 **GQA(Grouped Query Attention)** / **MQA**는 KV 헤드 수를 줄여 **KV 용량**을 깎는 설계다.

| | MHA | GQA | MQA |
|---|---|---|---|
| KV 헤드 | Q와 동일 경향 | Q보다 적음 | 더 적음(극단 1) |
| KV 메모리 | 큼 | 중간 | 작음 |
| 서빙 | 동시성↑ 여지 | 실무에 흔함 | 구현·품질 트레이드오프 |

LLaMA·Qwen 등 **Dense 사례** 다수가 GQA를 채택한 세대가 있다.  
**사실:** 어느 세대가 어떤 KV 헤드인지는 카드/config가 진실.  
**해석:** “Dense면 KV가 항상 같다”는 틀리다. Dense 안에도 KV 절감 축이 있다.

### 15. MoE를 지도에 다시 꽂기（미리보기 심화）

Attention은 Dense와 같고 FFN만 희소인 패턴이 흔하다 → **KV는 그대로**.  
서빙 차이는 주로:

- 전문가 가중치 상주
- 라우팅·expert parallel 통신
- 토큰별 비균일 실행

상세는 제109강. 여기선 “계열 태그 `MoE-Decoder`를 붙일 조건”만: config에 `num_experts` 등이 보이면 Dense 카드에 머무르지 말 것.

### 16. Hybrid/SSM — 상태와 KV가 공존할 때

```text
층 0..i-1: SSM/linear   → 고정 크기 상태 s
층 i..L-1: Attention    → KV cache 구간
```

질문 리스트:

1. Attention 층 비율은?
2. 상태 dtype·크기·체크포인트 규칙은?
3. Prefill에서 SSM 스캔 커널이 있는가?
4. 엔진이 hybrid graph를 지원하는가?

비율이 높을수록 KV 압박은 줄 수 있지만, **미지원 엔진**이면 최적의 Dense보다 못하다. 생태계가 성능의 일부다.

### 17. MTP를 지도에 꽂기

훈련 목표에 다중 위치 손실이 있거나, 추론 헤드가 여러 미래 토큰을 내는 설계면 `prediction=mtp` 태그.

서빙에서는:

- 엔진 speculative 경로와 결합 가능 여부
- 수락률 모니터링(제110·107)
- “품질 동일성” 주장의 근거(논문·테스트) 확인

### 18. 사례 배치 — GLM · LLaMA · Qwen

| 사례 | 1차 계열 읽는 법 | 서빙에서 먼저 볼 것 |
|---|---|---|
| LLaMA 계열 Dense | Dense decoder-only (+세대별 GQA 등) | KV, 양자화 레시피, 엔진 지원 |
| Qwen Dense | 동일 골격 + 제품별 길이/데이터 | 템플릿·토크나이저 일치 |
| Qwen/기타 MoE 변형 | 이름에 MoE가 보이면 **계열 재분류** | expert·엔진 지원 |
| GLM 계열 | Dense 또는 해당 세대 문서의 구조 | **GLM만의 특수 구조로 108강을 축소하지 말 것** |

브랜드가 MoE·hybrid로 분기하면 카드를 새로 쓴다.

### 19. 작은 “구조 → 지표” 의사결정 트리

```text
KV가 길이비례로 큰가?
  yes → PagedAttention·동시성·GQA 여부 확인 (105·106)
활성 FFN이 희소인가?
  yes → MoE 메모리·통신 (109)
한 스텝 다중 토큰 후보인가?
  yes → speculative/MTP (110)
Attention 외 믹서가 있나?
  yes → hybrid 지원·상태 (엔진 문서)
전부 no에 가까움 → Dense 기준 튜닝 (103·107·111)
```

### 20. 실습 — config 읽기 체크리스트

공개 config/json을 열어(환경에 파일이 있을 때) 다음을 채워 본다. 없으면 `unknown`.

```text
hidden_size / num_layers / num_attention_heads / num_key_value_heads
intermediate_size
num_experts / num_experts_per_tok   # MoE일 때
# hybrid 필드명은 모델마다 상이 → 문서
```

`num_key_value_heads < num_attention_heads` 이면 GQA/MQA 후보.

### 21. 자주 하는 실수

1. 108강을 “GLM만의 구조”로 축소해 Dense/MoE/Hybrid 비교를 생략
2. 브랜드 이름만으로 커널 최적화 여부를 단정
3. MoE를 “작으니 항상 빠름”으로 오해 (가중치 메모리·통신)
4. SSM을 “KV 없음 = 만능”으로 오해
5. MTP 훈련 모델인데 speculative 서버 설정을 안 켜고 TPOT만 비난
6. 엔진이 해당 아키텍처를 미지원인데 지표만 반복 측정
7. GQA를 무시하고 KV 용량을 MHA 공식으로만 계산
8. 계열 태그 없이 제107 리포트에 모델명만 기입

### 21.5 토크나이저·템플릿도 “구조”의 일부인가?

엄밀한 신경망 구조는 아니지만, 서빙에서는 **특수 토큰·chat template**이 틀리면 품질·길이가 달라져 지표가 흔들린다.

계열 카드에 한 줄:

```text
tokenizer_id / chat_template_hash: <기록 또는 unknown>
```

같은 Dense 계열이라도 템플릿이 다르면 출력 길이 분포가 바뀌고 TPOT 비교가 오염된다. 제107강 `method`와 함께 적는다.

### 21.6 양자화 레시피는 계열과 직교

INT4/FP8 등은 제103강의 축이다. 그러나:

- MoE는 전문가 가중치 용량 때문에 양자화 유혹이 ↑
- Dense GQA는 KV dtype 양자화와 시너지 여지
- Hybrid는 커널 지원 행렬이 더 稀疏할 수 있음

Family Card에 `quant_recipe: <name|none>`을 남겨, “구조 문제인지 정밀도 문제인지”를 분리한다. **숫자를 책에 쓰지 말 것.**

### 21.7 한 페이지 요약 — 계열 비교（수치 없음）

```text
Dense Decoder-only
  compute: Attn + dense FFN every token
  memory growth: KV ∝ layers × kv_heads × T
  serving levers: paging, batching, quant, TP
  examples: LLaMA / Qwen Dense / GLM (as family instances)

MoE Decoder-only
  compute: Attn + top-k experts
  memory: experts resident (+ KV)
  serving levers: engine MoE kernels, EP, load balance, quant
  detail: Lecture 109

MTP / Speculative-ready
  compute: draft + verify paths
  memory: KV + draft buffers
  serving levers: acceptance, gamma, engine flags
  detail: Lecture 110

Hybrid / SSM mix
  compute: depends on layer mix
  memory: partial KV + recurrent/SSM state
  serving levers: kernel maturity, engine support matrix
```

이 요약은 **암기 카드**다. 벤치 숫자 칸은 비워 두고 제107 템플릿으로만 채운다.

### 21.8 커리큘럼 위치 — 왜 108이 엔진 다음인가

제104~107이 엔진·지표를 준 뒤 구조를 여는 이유:

1. 지표 언어가 있어야 구조 차이를 **증상으로** 말할 수 있다
2. PagedAttention·스케줄러를 안 보면 MoE/Hybrid의 메모리 이야기를 오해한다
3. 반대로 구조 없이 엔진만 보면 “설정 노브”만 돌리다 미지원 아키텍처에 빠진다

108은 **엔진과 하드웨어(111) 사이의 모델 층**이다.

### 21.9 읽기 과제（선택）

특정 제품 백서를 읽을 때:

1. 제목을 브랜드가 아니라 **계열 태그**로 다시 쓴다
2. KV/전문가/상태/MTP 중 무엇이 명시됐는지 표시한다
3. 서빙 엔진 지원 문장이 있는지만 확인한다（속도 숫자는 제107 규칙으로 걸러 읽는다）

### 22. 핵심 정리

- 서빙 성능의 1차 분류는 브랜드가 아니라 **알고리즘 계열**이다.
- **Dense decoder-only**는 KV+밀집 FFN의 기준선이다. LLaMA·Qwen·GLM 등은 그 안의 사례로 읽는다.
- Dense 안에도 **GQA/MQA**처럼 KV를 줄이는 변형이 있다.
- **MoE / MTP / Hybrid·SSM**은 각각 활성 계산·예측 폭·상태 표현을 바꾼다.
- 구조 → KV·compute·통신 → TTFT/TPOT/Throughput으로 화살표를 그릴 것.
- Family Card + 엔진 지원 확인이 벤치 숫자보다 앞선다.
- 이름·버전은 변한다. **패턴과 측정 템플릿**은 남는다.

### 23. 핵심 용어

| 용어 | 설명 |
|---|---|
| Dense decoder-only | 인과 Attention+밀집 FFN 스택의 표준 LM |
| GQA/MQA | KV 헤드를 줄여 캐시 용량을 깎는 Attention 변형 |
| MoE | 전문가 라우팅으로 FFN을 희소 활성화 |
| MTP | 다중 토큰 예측 목표/헤드 변이 |
| SSM | 상태공간·선형 시계열 믹싱 계열의 총칭(세부는 모델별) |
| Hybrid | Attention과 non-attention 믹서를 층 단위로 혼합 |
| Family Card | 서빙용 계열·KV·엔진 지원 요약 카드 |
