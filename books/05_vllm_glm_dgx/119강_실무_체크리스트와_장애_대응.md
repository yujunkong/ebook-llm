# 제119강. 실무 체크리스트와 장애 대응

> **학습 목표**
> - 배포 전·중·후 체크리스트를 항목으로 실행한다
> - TTFT 급증 · OOM · NCCL 실패 · 품질 붕괴 등을 증상 → 가설 → 확인 → 조치로 나눈다
> - 롤백·회로차단·에스컬레이션 기준을 문장으로 적는다
> - 제120강 총정리 전에 “서빙이 학습과 다른 실패 모드를 갖는다”는 좌표를 고정한다

---
## 1. 왜 이것을 배우는가

학습 장애는 종종 loss 스파이크·NaN으로 보인다. 서빙 장애는 다음처럼 보인다.

| 사용자 증상 | 내부에서 자주 보이는 것 |
|---|---|
| “첫 응답이 안 온다” | Prefill 큐 적체, TTFT p95 폭발 |
| “말하다 끊긴다” | Decode 지연, 워커 death, 타임아웃 |
| “갑자기 바보가 됐다” | 템플릿·토크나이저·양자화·잘못된 가중치 |
| “가끔만 500” | OOM 재시작, NCCL, 디스크, 레이트리밋 |

제118강 baseline이 없으면 “느린가?”를 논쟁으로 푼다. baseline이 있으면 **회귀**로 푼다.

## 2. 운영 목표 — SLO 스케치

숫자 목표는 조직마다 다르다. 이 책은 임의 SLO 수치를 박지 않는다. 대신 **정의 칸**을 둔다.

| 지표 | SLO 칸（조직이 채움） | 측정 소스 |
|---|---|---|
| 가용성 | `(예: 월간 …)` | 헬스체크 성공률 |
| TTFT p95 | `(기입)` | 118과 동일 method |
| 에러율 | `(기입)` | 5xx / 타임아웃 |
| 품질 smoke | `(기입)` | 필수 프롬프트 통과율 |

SLO를 정하기 전이라도 **알람 임계**는 “지난주 p95의 급변”처럼 상대치로 시작해도 된다. 단, method를 바꾼 날은 임계를 재보정한다.

## 3. 배포 전 체크리스트（Pre-flight）

### 3.1 모델·토큰

- [ ] 체크포인트 경로·리비전 해시 확인
- [ ] 토크나이저·`chat_template`이 학습/평가와 동일（제72강）
- [ ] special token·중지 조건（EOS）확인
- [ ] 양자화 포맷이 엔진에서 로드되는지 dry-run
- [ ] 라이선스·사용 정책 확인（조직 절차）

### 3.2 엔진·병렬

- [ ] framework/version 고정（이미지 태그 pin）
- [ ] TP/PP 차수와 GPU count 일치（제113강）
- [ ] max context · max_num_seqs · KV dtype 명시
- [ ] 워밍업 요청 성공
- [ ] `/health` 또는 동등 엔드포인트 200

### 3.3 인프라

- [ ] `nvidia-smi`에 예상 GPU만 보이는지
- [ ] 드라이버/CUDA와 엔진 호환 표 대조
- [ ] 디스크: 모델·로그·스크래치 여유
- [ ] 네트워크: 멀티 노드면 NCCL/RoCE 사전 점검（제114~115강）
- [ ] 시계 동기（분산 로그 상관용）

### 3.4 관측·보고

- [ ] 메트릭 스크rape（TTFT, 큐 길이, GPU util, VRAM）
- [ ] 로그 구조화（request_id）
- [ ] 제118 형식 baseline 행이 “현재 릴리스”로 태깅됨
- [ ] 롤백 이미지/태그 문서화

하나라도 치명 항목이 비면 **배포하지 않는다**. “나중에 모니터링 달자”는 장애 후에 비용이 크다.

## 4. 배포 중 체크리스트（Rollout）

```text
canary (작은 트래픽)
  → smoke prompts
    → 지표 비교 vs baseline
      → 단계적 확대
        → 문제 시 즉시 rollback
```

- [ ] canary 비율·대상 명시
- [ ] smoke: 짧은/긴/거부/도구호출(쓰는 경우) 각 1+
- [ ] TTFT p95·에러율이 baseline 대비 급악화하면 중단
- [ ] 설정 diff（환경변수·yaml）를 릴리스 노트에 첨부

Canary 없이 전량 교체는 실수가 전 사용자에게 증폭된다.

## 5. 배포 후 체크리스트（Soak）

- [ ] 첫 30~120분 집중 감시（조직이 시간 칸 채움）
- [ ] VRAM 누수성 증가 없는지
- [ ] 로그에 NCCL/CUDA Xid 없는지
- [ ] 디스크 충만 경보
- [ ] 온콜 핸드오프 문서에 릴리스 링크

## 6. 일상 운영 체크리스트（짧은 버전）

매일/매 교대:

1. 헬스·레디니스
2. 에러율·TTFT p95 대시보드
3. GPU 온도·전력·ECC（있으면）
4. 큐 길이·거절 수
5. 디스크·인증서 만료
6. 백필/배치 잡이 온라인과 GPU 충돌하는지

주간:

1. 118 리포트 형식의 회귀 벤치 1회
2. 의존성 취약점·이미지 갱신 검토
3. 장애 티켓 회고 1건 이상（있으면）

## 7. 장애 대응 원칙

1. **사용자 영향부터 멈춘다**（롤백·트래픽 차단·읽기전용）
2. **시간을 남긴다**（timeline）
3. **가설을 하나만 시험**（117과 같은 통제）
4. **변경과 관측을 짝으로**（knob ↔ metric）
5. **복구 후 회고**（재발 방지 항목 → 체크리스트 흡수）

디버깅 중 동시에 TP를 바꾸고 quant를 바꾸고 프롬프트를 바꾸면 원인 불명으로 남는다.

## 8. 증상별 대응 트리

아래 트리의 “임계” 숫자는 비운다. 조직 baseline으로 대체한다.

### 8.1 TTFT 급증

```text
증상: TTFT p95 상승, 첫 토큰 지연 호소
  ├─ 큐 길이 ↑ ?  → 동시성/트래픽/워커 수 점검, 회로차단
  ├─ 입력 길이 ↑ ? → Prefill 비용, 프롬프트 캐시·한도
  ├─ GPU util 낮고 대기 ? → 스케줄러·락·CPU 병목·I/O
  ├─ GPU util 포화 ? → 용량 부족, 스케일/거절 정책
  └─ 최근 배포 ? → canary diff, 즉시 rollback 후보
```

확인 명령 예（환경에 맞게）:

```bash
# 큐/헬스 — 엔진 메트릭 엔드포인트 사용
curl -sS "$BASE/health"
# GPU
nvidia-smi --query-gpu=utilization.gpu,memory.used --format=csv -l 5
```

### 8.2 Throughput 저하 · TPOT 악화

```text
증상: 토큰 스트림이 버벅임
  ├─ 출력 길이 분포 변화?（reasoning↑） → 용량 재계산
  ├─ 배치/동시성 과다 → KV thrash, 되레 지연
  ├─ 열 스로틀 → 냉각·전력 한도
  └─ 커널/버전 회귀 → 이미지 pin 비교
```

정렬 이후 평균 출력 토큰이 늘 수 있다는 점은 제98~107강에서 이미 예고했다. **품질 개선이 서빙 부하**가 될 수 있다.

### 8.3 OOM · 워커 재시작

```text
증상: 5xx 스파이크, 컨테이너 restart, CUDA OOM
  ├─ max_num_seqs / context 과다 → 한도 하향
  ├─ 누수·단편화 → 재시작 후 재발 여부, 페이지 설정
  ├─ 동시 긴 컨텍스트 집중 → 입장 제어
  └─ 양자화/TP 재평가 → 117 행렬의 안전 지대
```

응급 조치 우선순위: **트래픽 제한 → 한도 하향 → 롤백 → 수평 확장**.

### 8.4 NCCL / 멀티 GPU 기동 실패

```text
증상: tp>1 기동 hang, NCCL timeout, 불균등 GPU
  ├─ count와 tp 불일치
  ├─ 가시 장치（CUDA_VISIBLE_DEVICES）오설정
  ├─ 패브릭/RoCE/방화벽（114~115）
  └─ 버전 미스매치（드라이버↔NCCL↔엔진）
```

단일 GPU로 임시 축소（기능 저하 모드）가 가능하면 **서비스 유지 후 디버깅**이 낫다.

### 8.5 품질 붕괴（느린데 이상함이 아님）

```text
증상: 거부율 폭주, 난해한 토큰, 언어 붕괴
  ├─ 잘못된 체크포인트/양자화 파일
  ├─ chat template·시스템 프롬프트 드리프트
  ├─ temperature 등 디코딩 설정
  ├─ 프록시가 다른 모델로 라우팅
  └─ 안전 필터/가드 오작동
```

성능 메트릭이  Greener 해도 품질 smoke가 빨갛면 **롤백 대상**이다. 118의 smoke quality 열을 운영 관문에 포함하라.

### 8.6 부분 장애 · “가끔”만 실패

```text
증상: 간헐 타임아웃
  ├─ 특정 긴 요청만? → 길이 한도·타임아웃 튜닝
  ├─ 특정 노드만? → 하드웨어 Xid, NIC
  ├─ 특정 시간대? → 배치 잡 충돌
  └─ GC/로그 폭주? → 디스크·저널
```

request_id로 한 건을 끝까지 추적할 수 없으면 간헐 장애는 거의 안 잡힌다.

## 9. 심각도 · 에스컬레이션

| 등급 | 정의 칸 | 초기 대응 |
|---|---|---|
| SEV1 | 전면 장애·데이터 위험 | 즉시 롤백/차단, 음성 에스컬레이션 |
| SEV2 | 심각한 지연·부분 장애 | canary 중단, 온콜+오너 |
| SEV3 | 제한적 영향 | 티켓·근무시간 수정 |
| SEV4 | 화장·문서 | 백로그 |

등급 숫자 자체보다 **누가 몇 분 안에 모이는지**를 runbook에 적는다.

## 10. 롤백 Runbook（최소）

```text
1. 트래픽을 이전 레비전으로（또는 서비스 스케일 0 후 교체）
2. 헬스 확인
3. smoke prompts
4. 사용자 공지（조직 절차）
5. 장애 브랜치에 원인 가설 기록
6. 재배포는 원인 완화 후에만
```

“핫픽스로 설정 12개를 한 번에”는 롤백 이후에 한다.

## 11. 회로차단 · 입장 제어

서빙에서 유용한 보호:

| 장치 | 역할 |
|---|---|
| max concurrency | 과입 방지 |
| max request length | Prefill 폭탄 방지 |
| timeout | 무한 대기 방지 |
| bulkhead | 온라인 vs 배치 분리 |
| load shed | 의도적 거절로 전체 보호 |

거절은 실패가 아니라 **잔여 사용자를 위한 성공**일 수 있다. 단, 거절 메시지를 측정에 포함해 조용한 용량 부족을 숨기지 않는다.


회고 없이 지나간 장애는 같은 체크리스트 구멍을 남긴다.

## 13. 보안·남용（서빙 관점 최소）

이 강의의 범위는 추론 스택이지만, 운영 체크에 최소 항목은 넣는다.

- [ ] API 인증·쿼터
- [ ] PII 로그 마스킹 정책
- [ ] 모델 가중치 경로 권한
- [ ] 프롬프트 인젝션 가드（제품 요구 시）
- [ ] 의존성/이미지 스캔

세부 보안 공학은 별도 문서. 여기서는 “열려 있는 엔드포인트에 모델 올렸다”가 체크리스트에 남는지 확인한다.

## 15. 실습

1. 자신의 116 스택에 대해 Pre-flight 체크리스트를 실제로 기입한다（빈칸 남기지 않기）.
2. “TTFT 급증” 트리를 팀 메트릭 이름에 맞게 한 페이지 runbook으로 옮긴다.
3. 의도적 장애 주입 하나（예: max_num_seqs 과다, 잘못된 template）를 **스테이징**에서 재현하고, Incident 템플릿을 채운다.
4. 118 baseline 행 ID를 “롤백 판단 기준”으로 runbook에 링크한다.

프로덕션에서 임의 장애 주입 금지.

## 16. 자주 하는 실수

1. 모니터링 없이 배포
2. 롤백 경로 미검증（롤백이 더 안 됨）
3. 증상 논의만 하고 트래픽을 안 줄임
4. 품질 회귀를 성능 대시보드만 보고 놓침
5. 사후 체크리스트 미갱신
6. request_id 없이 로그 바다에서 수영

## 17. 핵심 정리

- 실무 체크리스트는 배포 전·중·후·일상으로 나눈다.
- 장애 대응은 영향 완화 → 통제된 가설 → 롤백/수정 → 회고다.
- TTFT·OOM·NCCL·품질은 서로 다른 트리다.
- baseline 없는 온콜은 추측 온콜이다.
- 다음 강의는 5권과 전권을 **밑바닥에서 Serving까지** 한 줄로 닫는다.

## 18. 핵심 용어

| 용어 | 한 줄 의미 |
|---|---|
| Runbook | 증상별 절차서 |
| Canary | 소량 트래픽으로 새 버전 검증 |
| Rollback | 이전 정상 레비전 복귀 |
| SLO | 서비스 수준 목표 |
| Load shedding | 과부하 시 의도적 거절 |
| Soak | 배포 후 안정 감시 구간 |
| SEV | 장애 심각도 등급 |
| Smoke test | 최소 기능·품질 확인 |

성능 지표는 정상인데 답변이 붕괴했다. 우선 확인할 항목 두 가지를 쓰시오.

## 정답 및 해설

### 문제 1

학습과 서빙의 문자열 조립이 어긋나면 동일 가중치라도 동작·품질이 달라진다.

### 문제 2

교락으로 원인 귀속이 불가능해진다（117의 통제 실험과 동일 원리）.

### 문제 3

요청이 GPU 계산 전에 대기열에서 시간을 소비해 첫 토큰 시각이 밀린다.

### 문제 4

예: 체크포인트/양자화 파일 오류, chat template·라우팅·디코딩 설정（두 가지면 충분）.

### 문제 5

“느리다/빠르다”를 회귀로 판정할 기준 조건·수치가 되기 때문이다.

### 문제 6

예: Serving 기동 → 통제 최적화 실험 → 감사 가능 리포트 → 운영·장애 runbook까지 이어진 실무 루프.

## 20. 다음 강의와 연결

체크리스트와 runbook까지 있으면 5권의 실무 고리는 닫힌다.

**제120강. 5권·전권 총정리 — 밑바닥에서 Serving까지**는 1권 Python에서 5권 Serving까지를 한 경로로 다시 접는다. 새 엔진 튜닝을 시작하지 않는다. 좌표를 고정하고 책을 끝낸다 — 챗봇 데모로 끝내지 않는다.
