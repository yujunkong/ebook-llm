# 117강. 프로젝트 — GPU 최적화 실험
## 이번 강에서 배우는 내용

- Quantization · Batch · Context · Tensor Parallel(TP)을 독립 축으로 분리해 실험한다
- 각 축이 TTFT · TPOT · Throughput · VRAM에 주는 방향을 가설 → 측정 → 해석으로 적는다
- `ch117_gpu_opt/`에 재현 가능한 실험 스크립트·설정·리포트 뼈대를 둔다
- 제118강의 성능 리포트 템플릿에 넣을 원시 측정 행을 남긴다

## 왜 중요한가?
서빙 문서에는 “양자화하면 빠르다”, “배치를 키우면 처리량이 오른다” 같은 문장이 많다. 그러나 실제로는 축이 얽힌다.

| 흔한 말 | 실험에서 드러나는 것 |
|---|---|
| INT4면 항상 이득 | 커널·교정·품질·긴 컨텍스트에서 이득이 뒤집힐 수 있음 |
| 배치↑ = 처리량↑ | KV·스케줄러 한계에서 TTFT가 악화될 수 있음 |
| 컨텍스트↑ = 느려짐 | Prefill 지배 vs Decode 지배가 국면마다 다름 |
| TP↑ = 항상 확장 | 통신 오버헤드가 이득을 잠식할 수 있음 |

제107강에서 지표를 정의했고, 제103·113강에서 Quant·TP를 배웠다. 이번 프로젝트는 그 지식을 **통제 실험**으로 옮긴다.

## 제116강과의 연결
```text
116: Serving이 "켜진다"          ← 동작 증거
117: Serving이 "측정·비교된다"   ← 최적화 증거
118: 측정이 "보고서로 남는다"    ← 전달 증거
```

제116강 산출물 가정:

- 엔진이 OpenAI 호환 또는 동등 HTTP로 응답한다
- 모델 경로·토크나이저·chat template이 고정되어 있다
- GPU 대수·드라이버·엔진 버전이 기록 가능하다

116이 없으면 이 강의의 최소 대체는 **로컬에서 동일 엔진·동일 모델로 단일 서버를 기동**하는 것이다. 비교의 핵심은 “프로덕션급”이 아니라 **통제**다.

## 실험 행렬 설계
### 7.1 축 정의

```text
축 Q  Quantization :  메모리·대역·커널 경로
축 B  Batch/Concurrency :  스케줄·KV 점유·처리량
축 C  Context length :  Prefill 비용·KV 성장
축 T  Tensor Parallel :  모델 샤드·통신
```

한 실험 포인트:

$$

x = (Q, B, C, T)

$$

비교할 때는 **한 좌표만** 바꾼다.

$$

x' = (Q+\Delta Q,\ B,\ C,\ T)

$$

### 7.2 권장 격자（최소）

GPU·모델 규모에 맞게 숫자를 줄여도 된다. 아래는 **템플릿**이다. 칸의 값은 예시 레이블이며, 성능 수치가 아니다.

| 축 | 조건 1 | 조건 2 | 조건 3 | 조건 4(선택) |
|---|---|---|---|---|
| Q | `bf16/fp16` | `fp8`(지원 시) | `int8` 또는 weight-only | `int4`(AWQ/GPTQ 등) |
| B | `c=1` | `c=4` | `c=16` | `c=32` |
| C | `in=128` | `in=1024` | `in=4096` | `in=8192`(가능 시) |
| T | `tp=1` | `tp=2` | `tp=4`(GPU 충분 시) | — |

Baseline 예:

```text
Q=bf16, B=c=4, C=in=1024/max_out=128, T=tp=1
```

### 7.3 조합 폭발 막기

전부 교차하면 $4\times4\times4\times3=192$다. 초안 규칙:

1. Baseline 고정
2. 축마다 Baseline에서만 sweep（약 3+3+3+2 = 11포인트 + baseline）
3. 유망한 2축만 사후 교차（예: 최선 Q × 최선 B）

교육 프로젝트의 합격선은 **축별 sweep 완료**다.

## 부하·프롬프트 설계
### 8.1 왜 프롬프트를 고정하는가

입력 길이·출력 길이가 바뀌면 Prefill/Decode 비율이 바뀐다. “최적화가 이득”인지 “입력이 짧아짐”인지 구분되지 않는다.

규칙:

1. 동일 `prompts/` 파일을 모든 조건에서 사용
2. `max_tokens`(또는 `max_new_tokens`) 고정
3. temperature 등 샘플링은 벤치 모드에서 deterministic에 가깝게（`temperature=0` 등）
4. 시스템 프롬프트·chat template 고정（제72·116강）

### 8.2 길이 버킷

| 파일 | 역할 |
|---|---|
| `short.txt` | Decode 비중 관찰용 짧은 입력 |
| `medium.txt` | Baseline 주력 |
| `long_template.txt` | Prefill·KV 압박용. 반복 패딩은 **토큰 수 목표**만 맞추고 의미 품질은 요구하지 않음 |

긴 입력을 만들 때 임의 인터넷 저작권을 붙여넣지 않는다. 합성 반복·라이선스 명확 텍스트를 쓴다.

## 측정 방법（Method）
제107강 정의를 프로젝트 언어로 옮긴다.

| 지표 | 정의(운영형) | 주의 |
|---|---|---|
| TTFT | 요청 송신 → 첫 토큰(또는 첫 chunk) 수신 | 네트워크·JSON 파싱 포함 여부를 명시 |
| TPOT | (마지막 토큰 시각 − 첫 토큰 시각) / (출력토큰−1) | 출력 1토큰이면 정의 불가 → 제외 |
| Throughput | 완료 요청 수 / 벽시계, 또는 생성 토큰 수 / 벽시계 | 요청/초와 토큰/초를 섞어 쓰지 말 것 |
| Peak VRAM | `nvidia-smi` 샘플 또는 엔진 메트릭 | 다른 프로세스 제외 여부 기록 |

### 9.1 Warm-up

첫 수 회는 컴파일·캐시·페이지 할당으로 오염된다.

```text
warm-up: 동일 설정으로 N회 (결과 폐기)
measure: M회 기록
```

$N,M$은 환경에 맞게. 리포트에 숫자를 적는다（예: N=3, M=10）. **구체적인 속도 수치를 이 책에 박지 않는다.**

### 9.2 동기 vs 비동기

| method 레이블 | 의미 |
|---|---|
| `sync_serial` | 한 요청씩. TTFT/TPOT 분산 파악에 유리 |
| `async_conc_K` | 동시성 K. 처리량·큐잉 지연 포함 |
| `engine_bench` | 엔진 내장 throughput 벤치(있다면). 정의를 엔진 문서와 대조 |

같은 표에 `sync`와 `async`를 섞어 “개선”이라고 쓰지 않는다.

### 10.1 `bench_once.py`（개념）

```python
# ch117_gpu_opt/scripts/bench_once.py
"""단일 조건 측정 스케치. 실제 HTTP 스키마는 116강 서버에 맞출 것."""

from __future__ import annotations

import argparse
import json
import time
from dataclasses import asdict, dataclass
from typing import Any

@dataclass
class RunMeta:
    model: str
    quant: str
    gpu: str
    count: int
    context_in: int
    max_out: int
    batch_or_conc: int
    framework: str
    version: str
    method: str

@dataclass
class RunMetrics:
    ttft_s: float | None
    tpot_s: float | None
    out_tokens: int | None
    wall_s: float | None
    ok: bool
    error: str | None = None

def measure_one(url: str, prompt: str, max_out: int) -> RunMetrics:
    """스트리밍 응답을 가정한 의사코드형 구현.

    실제로는 httpx/openai SDK 등으로 chunk 시각을 잰다.
    이 함수는 '어디에 시계를 둘지'를 고정하기 위한 뼈대다.
    """
    t0 = time.perf_counter()
    first = None
    last = None
    out_tokens = 0
    try:
        # stream = client.chat.completions.create(..., stream=True)
        # for chunk in stream:
        #     now = time.perf_counter()
        #     if first is None: first = now
        #     last = now
        #     out_tokens += count_tokens(chunk)
        raise NotImplementedError("116강 서버 클라이언트에 연결해 구현")
    except Exception as e:  # noqa: BLE001 — 벤치에서 실패도 기록
        return RunMetrics(None, None, None, time.perf_counter() - t0, False, str(e))

    # 아래는 구현 완료 후 계산 예시
    assert first is not None and last is not None
    ttft = first - t0
    tpot = None
    if out_tokens > 1:
        tpot = (last - first) / (out_tokens - 1)
    return RunMetrics(ttft, tpot, out_tokens, last - t0, True, None)

def main() -> None:
    p = argparse.ArgumentParser()
    p.add_argument("--meta-json", required=True)
    p.add_argument("--out-jsonl", required=True)
    p.add_argument("--prompt-file", required=True)
    p.add_argument("--url", required=True)
    args = p.parse_args()

    meta = RunMeta(**json.loads(open(args.meta_json, encoding="utf-8").read()))
    prompt = open(args.prompt_file, encoding="utf-8").read()
    metrics = measure_one(args.url, prompt, meta.max_out)

    row: dict[str, Any] = {**asdict(meta), **asdict(metrics), "metric_set": "ttft_tpot_wall"}
    with open(args.out_jsonl, "a", encoding="utf-8") as f:
        f.write(json.dumps(row, ensure_ascii=False) + "\n")

if __name__ == "__main__":
    main()
```

## 축별 가설과 관찰 포인트
수치는 비운다. **방향 가설**만 적고, 측정으로 확인·반증한다.

### 11.1 Quantization（Q）

| 관찰 칸 | 기입 |
|---|---|
| 가설 | 비트↓ → VRAM↓, 때로 tok/s↑. 품질·커널 미지원 시 역효과 가능 |
| 고정 | B, C, T, model, method |
| 측정 | peak VRAM, Throughput, （가능하면）간이 품질 체크 |
| 결과 | `(실측 기입)` |
| 실패 | OOM 해소 여부, 기동 실패, 이상 토큰 |

품질 체크는 “장문 미학”이 아니라 **동일 프롬프트 출력 diff·필수 문자열 포함** 정도면 충분하다.

### 11.2 Batch / Concurrency（B）

| 관찰 칸 | 기입 |
|---|---|
| 가설 | c↑ → Throughput↑ 경향, TTFT p95↑ 가능（큐잉） |
| 고정 | Q, C, T |
| 측정 | Throughput, TTFT p50/p95, TPOT |
| 결과 | `(실측 기입)` |
| 실패 | 타임아웃, KV full, 스케줄러 거부 |

Continuous Batching（제102강）이 켜진 엔진에서는 “배치 크기” 의미가 학습 때와 다르다. **동시 인플라이트 요청 수**로 말하라.

### 11.3 Context（C）

| 관찰 칸 | 기입 |
|---|---|
| 가설 | 입력↑ → Prefill·TTFT↑, KV↑. Decode TPOT은 상대적으로 덜 변할 수 있음 |
| 고정 | Q, B, T, max_out |
| 측정 | TTFT, peak VRAM, prefill 관련 엔진 메트릭(있으면) |
| 결과 | `(실측 기입)` |
| 실패 | 최대 길이 초과, 페이지 할당 실패 |

### 11.4 Tensor Parallel（T）

| 관찰 칸 | 기입 |
|---|---|
| 가설 | 파라미터가 GPU당 한계를 넘을 때 필수. 작 모델·짧 입력이면 통신 비용 > 이득 가능 |
| 고정 | Q, B, C, 동일 노드 패브릭 |
| 측정 | Throughput, TTFT, GPU당 VRAM, （가능하면）통신 시간 비율 |
| 결과 | `(실측 기입)` |
| 실패 | NCCL 오류, 불균등 샤드, 기동 hang |

제114강 NCCL/RoCE 이슈가 여기로 올라온다. TP 실험은 **멀티 GPU가 있을 때만** 필수 성공 조건으로 한다. 단일 GPU면 `tp=1`만 하고 축 T는 “환경상 스킵 + 이유”로 적는다.

## 해석 프레임 — 숫자 없이 쓰는 법
실측을 채운 뒤 해석은 다음 문장 틀만 허용한다.

```text
1) 관찰: [metric]이 [조건 A] 대비 [조건 B]에서 [증가/감소/유사]했다.
2) 통제: 바꾼 축은 [Q/B/C/T]뿐이며 method는 동일하다.
3) 기전 후보: (예) KV 증가 / 커널 효율 / 큐잉 / NCCL 비율 …
4) 반증 가능성: (예) 워밍업 부족, 백그라운드 GPU 점유, 클럭 스로틀
5) 결정: 다음으로 교차 실험할 축은 …
```

“업계 평균 대비 32% 향상”처럼 **출처 없는 비교문**은 금지다.

## 수학적 보조 — 대략 비용 스케치
정확한 FLOPs를 주장하지 않는다. 실험 전 **주문이 맞는지** 보는 스케치다.

Prefill 주의 Attention 항（서열 길이 $L$, 헤드 차원 $d$, 층 $N$）:

$$

\mathrm{Cost}_{\mathrm{attn}}^{\mathrm{prefill}} \propto N \cdot L^2 \cdot d

$$

Decode 한 스텝（KV 캐시 사용）:

$$

\mathrm{Cost}_{\mathrm{attn}}^{\mathrm{decode\ step}} \propto N \cdot L_{\mathrm{cache}} \cdot d

$$

VRAM 중 KV 대략:

$$

\mathrm{Mem}_{\mathrm{KV}} \propto B_{\mathrm{inflight}} \cdot L \cdot N \cdot d_{\mathrm{kv}} \cdot b

$$

여기서 $b$는 바이트/요소（정밀도）, $B_{\mathrm{inflight}}$는 동시 서열 수다.

**해석:** Context 축은 $L$과 $L^2$ 감수성, Batch 축은 $B_{\mathrm{inflight}}$, Quant 축은 $b$와 matmul 커널, TP는 통신/계산 비를 흔든다.
