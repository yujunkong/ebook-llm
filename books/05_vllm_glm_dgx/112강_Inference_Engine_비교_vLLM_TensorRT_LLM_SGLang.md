# 제112강. Inference Engine 비교 — vLLM · TensorRT-LLM · SGLang

> **학습 목표**
> - vLLM, TensorRT-LLM, SGLang의 설계 목표·강조점을 개요 수준에서 구분한다.
> - PagedAttention, CUDA Graph / 엔진 그래프, Radix-style prefix cache 같은 키워드를 무엇에 좋은 도구인지로 연결한다.
> - “항상 가장 빠른 엔진”은 없다는 전제 아래 선택 기준 체크리스트를 만든다.
> - GB10 / DGX Spark 하드웨어 상세는 제115강으로 미루고, 여기서는 소프트웨어 엔진에 집중한다.

## 1. 왜 이것을 배우는가

서빙 스택을 고를 때 흔히 나오는 함정:

```text
함정 1: SNS/블로그의 “X가 제일 빠르다”를 그대로 채택
함정 2: 팀이 아는 엔진만 고집
함정 3: 하드웨어(DGX Spark 등)와 엔진을 한 덩어리로 혼동
함정 4: 연구 데모 설정과 24/7 운영 요구를 동일시
```

엔진은 **모델 가중치를 토큰 스트림으로 바꾸는 런타임**이다. 같은 모델이라도:

| 축 | 달라질 수 있는 것 |
|---|---|
| 처리량 | continuous batching·스케줄·커널 |
| 지연 | prefill 처리, 캐시 히트, 그래프 |
| 기능 | tool calling, structured output, multi-LoRA |
| 운영 | 빌드 복잡도, 버전 고정, 관측성 |
| 하드웨어 적합성 | GPU 아키텍처·정밀도·멀티노드 |

제115강의 2× DGX Spark는 **어디에 올릴지**이고, 이번 강의는 **무엇으로 돌릴지**다.

## 3. 비교의 규칙

이 강의의 규칙:

1. **설계 의도**를 먼저 말한다. 마케팅 문장을 승패로 읽지 않는다.
2. 기능은 **시점·버전에 따라 변한다**. 확정 목록처럼 암기하지 말고, 공식 문서 확인 습관을 남긴다.
3. 성능 수치는 **직접 측정하기 전엔 인용·발명하지 않는다**.
4. “A가 B를 대체한다”보다 **언제 A가 유리한 후보인가**를 말한다.

```text
좋은 질문: 우리 트래픽은 prefix 공유가 많은가? 그래프 고정이 가능한가?
나쁜 질문: 인터넷에서 제일 빠르다는 엔진이 뭐지?
```

## 4. 세 엔진 한눈에 (개요)

| 엔진 | 한 줄 설계 강조 (설명) | 이 책과의 위치 |
|---|---|---|
| **vLLM** | 처리량·메모리 효율 서빙, PagedAttention, 넓은 모델 생태계 | 제104~106, 116강 기본 실습 |
| **TensorRT-LLM** | NVIDIA 추론 스택·엔진 최적화·배포 파이프라인과의 결합 | 저지연·최적화 파이프라인 후보 |
| **SGLang** | 구조화·에이전트·프로그램적 생성과 Radix-style 캐시 | prefix·멀티턴·structured 워크로드 후보 |

설명: 세 줄 요약은 **출발 지도**다. 각 엔진은 시간이 지나며 서로의 강점을 흡수한다(예: 캐시·그래프·구조화 출력). 최신 지원 표는 릴리즈 노트를 본다.

## 5. vLLM — 처리량형 서빙의 기준점

### 5.1 설계 목표 (개요)

vLLM은 LLM 서빙에서 반복되던 문제를 정면으로 다룬다.

```text
문제: KV cache 파편화·비효율 → 배치를 못 키움 → 처리량 저하
대응: PagedAttention으로 KV를 페이지 단위로 관리 (제105강)
```

추가로 continuous batching 스케줄러(제106강)가 **들어온 요청을 멈추지 않고** 배치에 섞는다.

### 5.2 핵심 키워드

| 키워드 | 역할 |
|---|---|
| PagedAttention | KV 메모리 가상화·효율 |
| Continuous batching | 요청 단위 입장/퇴장 |
| OpenAI-compatible API | 실무 연동 표면 |
| 다양한 모델 지원 | 실험·교체 속도 |

### 5.3 언제 후보가 되는가

- 팀이 PyTorch·Hugging Face 흐름에 익숙하다.
- 모델 교체가 잦고, “일단 서빙을 올려 측정”이 우선이다.
- 처리량·메모리 효율이 중요하고, 커스텀 엔진 빌드 비용을 낮추고 싶다.
- 이 책의 프로젝트(제116강)처럼 **측정 루프를 먼저** 만들고 싶다.

### 5.4 주의할 점 (설명)

- “기본 설정”이 모든 GPU·모델에서 최적인 것은 아니다.
- 그래프·커널 백엔드·양자화 경로는 옵션·버전에 따라 다르다.
- 멀티노드 TP는 네트워크·NCCL 준비가 전제다(제113~115강).

## 6. TensorRT-LLM — 엔진 최적화·배포 밀착

### 6.1 설계 목표 (개요)

**TensorRT-LLM** 은 NVIDIA의 LLM 추론을 위한 라이브러리·런타임 계열로, **엔진 빌드·커널·그래프 최적화**와 배포 스택과의 결합을 강조하는 쪽에 가깝다.

직관:

```text
모델을 “범용 인터프리터”로만 돌리기보다
대상 GPU·정밀도·형상에 맞춘 실행 계획을 만들어 돌린다
```

(구체 빌드 플로·플래그는 버전 문서를 따른다.)

### 6.2 핵심 키워드

| 키워드 | 역할 (개요) |
|---|---|
| Engine build | 최적화 산출물 생성 |
| In-flight batching 등 | 서빙 중 배치 (명칭·구현은 문서 확인) |
| CUDA Graph / 실행 최적화 | 런치 오버헤드·커널 효율 |
| Quantization 통합 | FP8 등 경로와의 결합 (지원 범위는 문서) |

### 6.3 언제 후보가 되는가

- 대상 하드웨어가 NVIDIA 스택으로 고정되어 있다.
- 모델·형상 변화가 상대적으로 적고, **빌드 비용 대비 런타임 이득**을 노린다.
- 저지연 SLA, 최적화 엔지니어 리소스, 기존 TensorRT 운영 경험이 있다.
- 컨테이너·NIM 등 NVIDIA 배포 경로와 맞추고 싶다.

### 6.4 주의할 점 (설명)

- 엔진 빌드·버전 고정·재현 파이프라인이 운영 부채가 될 수 있다.
- 모델이 자주 바뀌면 “빠른 실험” 측면에서 마찰이 생길 수 있다.
- “TensorRT-LLM이면 항상 더 빠르다”는 **측정 없는 주장**이다.

## 7. SGLang — 프로그램적 생성과 캐시

### 7.1 설계 목표 (개요)

**SGLang** 은 LLM을 **프로그램처럼 제어하는 생성 런타임** 쪽에 무게가 있다. 멀티턴, 도구 호출, 구조화 출력, 공유 prefix가 많은 워크로드에서 **캐시 재사용**을 설계 핵심으로 내세우는 편이다.

### 7.2 Radix-style prefix cache (개요)

아이디어(설명):

```text
여러 요청이 긴 시스템 프롬프트·도구 스키마·대화 앞부분을 공유
→ 그 KV/상태를 트리(radix) 형태로 재사용
→ 중복 prefill을 줄일 여지
```

제101강 KV Cache가 “한 요청의 과거”라면, radix-style cache는 **요청들 사이의 공유 과거**에 가깝다.

사실: 구현 명칭·API·히트율 통계는 버전·설정에 따른다.  
설명: prefix 공유가 거의 없는 완전 무작위 단발 트래픽에서는 이득이 작을 수 있다.

### 7.3 언제 후보가 되는가

- 에이전트·RAG·툴 사용으로 **동일 prefix가 반복**된다.
- constrained decoding / structured output이 제품 핵심이다.
- “생성 흐름을 프로그램으로 짜고” 그 위에서 성능을 보고 싶다.

### 7.4 주의할 점 (설명)

- 팀 익숙도·생태계·운영 툴링을 함께 본다.
- 캐시 이득은 **트래픽 패턴 함수**다. 벤치마크에 공유 prefix를 넣지 않으면 실서비스를 왜곡한다.
- 다른 엔진도 prefix caching 기능을 확장 중이므로, “캐시 = 특정 엔진 전유”로 단정하지 말 것.

## 8. 공통 기술 레고 — 용어 정렬

세 엔진을 비교할 때 같은 레고 블록이 다른 이름으로 나타난다.

### 8.1 Paged KV / 메모리 관리

- **무엇**: KV를 연속 거대 블록이 아니라 페이지·블록 단위로 관리
- **왜**: 파편화 감소, 더 큰 유효 배치
- **연결**: 제105강 PagedAttention

### 8.2 Continuous / in-flight batching

- **무엇**: 요청이 서로 다른 단계에서 한 GPU 배치에 공존
- **왜**: decode memory-bound 구간에서 효율↑ 여지 (제111강)
- **연결**: 제102, 106강

### 8.3 Graphs (CUDA Graph 등)

- **무엇**: 반복되는 커널 시퀀스를 그래프로 캡처해 런치 오버헤드를 줄임
- **왜**: 특히 decode처럼 짧은 커널이 반복될 때
- **제약**: 동적 shape·제어 흐름이 많으면 이득이 줄거나 비활성

### 8.4 Prefix / KV cache reuse

- **무엇**: 동일·공통 prefix의 KV를 재계산하지 않음
- **왜**: TTFT·prefill 비용 절감 여지
- **측정**: 캐시 히트율 없이 속도만 보면 원인 분석이 안 됨

### 8.5 Speculative decoding

- **무엇**: 제110강
- **엔진**: 지원 여부·알고리즘 옵션은 문서 확인
- **주의**: 수용률 낮은 도메인에서는 역효과 가능

| 기준 | 질문 | 메모 |

| 트래픽 패턴 | 단발 vs 멀티턴, prefix 공유율 | |

| 기능 | tool, JSON schema, vision, LoRA | |
| 하드웨어 | GPU 세대, 멀티노드, 통합 메모리 플랫폼 | |

결정 규칙 제안:

```text

3) “조금 더 빠름”보다 “장애 시 복구·설명 가능”을 명시적으로 가중한다
```

## 10. 워크로드별 경향 (단정이 아닌 경향)

| 워크로드 | 경향적 관찰 (설명) |
|---|---|
| 높은 동시성 챗봇 | batching·KV 효율이 큰 레버 |
| 긴 시스템 프롬프트 공유 | prefix cache 가치가 커짐 |
| 모델 주간 교체 A/B | 빌드 무거운 파이프라인은 마찰 |
| 초저지연 단일 스트림 | 그래프·커널·양자화·스케줄 미세조정 |
| 구조화 출력·에이전트 | 제약 디코딩·프로그램 런타임 비중↑ |
| 2노드 TP 실험 | 엔진보다 **네트워크·NCCL 준비**가 선행 (제114~115) |

다시 강조: 경향은 가설이다. **측정이 판결**이다.

## 11. “한 엔진이 항상 최고”가 아닌 이유

1. **워크로드 분포**가 다름 (prefix, 길이, 동시성).  
2. **버전**이 다름 (3개월 전 벤치 ≠ 오늘).  
3. **양자화·dtype**이 다름.  
4. **GPU·메모리 subsystem**이 다름 (제111, 115강).  
5. **공정한 비교**가 어려움 (워밍업, 캐시 상태, CPU 토크나이저, 네트워크).  
6. **제품 기능**이 속도보다 우선인 경우가 많음.

그래서 이 책은 승자 트로피 대신 **비교 프레임**을 준다.

## 12. 마이그레이션·공존 전략

실무에서는 엔진을 하나로 몰지 않기도 한다.

```text
예:
  연구/실험 클러스터 → vLLM
  특정 고정 모델 저지연 경로 → TensorRT-LLM
  에이전트 prefix-heavy 서비스 → SGLang
```

공존 시 필요한 것:

- 동일 관측 지표(제107강)
- 동일 프롬프트 세트
- 라우팅·모델 이름 규약
- 실패 시 폴백 정책(제119강)

## 13. 작은 의사결정 예제 (가상)

**가상 팀 A**

- 스타트업, 모델 2주마다 교체, HF 가중치, GPU 1~2장
- 동시성 중간, prefix 공유 보통

→ 후보: vLLM을 기본, 병목이 보이면 캐시·양자화·스케줄 튜닝. 다른 엔진은 **필요 근거가 생길 때** PoC.

**가상 팀 B**

- 고정 모델, NVIDIA 인프라, p99 TTFT 계약, 전담 추론 엔지니어

→ 후보: TensorRT-LLM 경로를 PoC에 포함. 다만 동일 트래픽으로 vLLM 등과 **나란히 측정**.

**가상 팀 C**

- 고객별 긴 시스템 프롬프트 + 툴 스키마 반복, 멀티턴 에이전트

→ 후보: SGLang 등 prefix/program 친화 런타임을 PoC. 벤치에 **실제 prefix 공유**를 넣을 것.

이 예는 처방전이 아니라 **질문 연습**이다.

## 15. 자주 하는 실수

1. 하드웨어 강의(구 GB10 제목)와 엔진 비교를 혼동한다 → 하드웨어는 **제115강**.  
2. 캐시 히트율 100% 벤치만 보고 실트래픽에 투영한다.  
3. API 호환만 보고 샘플링·토크나이저·스톱 토큰 차이를 무시한다.  
4. 엔진 교체로 네트워크 TP 문제를 해결하려 한다.  
5. 성능만 보고 온콜·보안·재현성을 0점 처리한다.

## 16. 핵심 정리

- vLLM · TensorRT-LLM · SGLang은 **다른 설계 강조**를 가진 서빙 엔진이다.
- Paged KV, batching, graphs, prefix cache는 공통 레고이며 이름·완성도는 엔진·버전마다 다르다.
- 선택은 체크리스트 → 동일 워크로드 측정 → 운영 가중치 순이 안전하다.
- **항상 최고인 엔진은 없다.** 가설을 측정으로 갈아끼운다.
- 다음 단계는 멀티 GPU로 가중치를 나누는 **Tensor Parallel**(제113강)이다.

## 17. 핵심 용어

| 용어 | 의미 |
|---|---|
| Inference Engine | 모델로 토큰을 생성하는 서빙 런타임 |
| vLLM | PagedAttention 기반 고효율 서빙 엔진 |
| TensorRT-LLM | NVIDIA 중심 최적화·엔진 빌드형 LLM 추론 스택 |
| SGLang | 프로그램적 생성·캐시 친화 런타임 |
| CUDA Graph | 커널 시퀀스 캡처로 런치 오버헤드 감소 |
| Prefix / Radix cache | 공유 앞부분 KV·상태 재사용 |
| PoC | 본채택 전 동일 조건 검증 |
